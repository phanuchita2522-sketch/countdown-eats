# CountDown Eats – เวอร์ชันเปิดใช้งานจริง (ไม่มีค่าใช้จ่ายตั้งต้น)

ติดตั้งเป็นเว็บแอป (PWA) บนมือถือได้เลย ไม่ต้องผ่านร้านแอป ภาษา: ไทย / English

## สิ่งที่เปลี่ยนในเวอร์ชันนี้
| เรื่อง | ก่อนหน้า | ตอนนี้ |
|---|---|---|
| ระบบกันโกง | ทำงานในเครื่องผู้ใช้ แก้โค้ดแล้วเลี่ยงได้ | **ทำงานที่เซิร์ฟเวอร์ทั้งหมด** (`supabase-setup.sql`) แอปเป็นแค่ตัวเรียก ตารางปิดไม่ให้อ่าน/เขียนตรง |
| ราคา/สต็อก/รหัสรับของ | ฝั่งแอปเป็นคนส่งมา | เซิร์ฟเวอร์คิดเอง แก้ราคาในเบราว์เซอร์ก็ถูกคิดราคาจริง ซื้อเกินสต็อกไม่ได้ ซื้อชิ้นสุดท้ายพร้อมกันได้คนเดียว |
| ข้อมูลรับเงินของร้าน | ผู้ใช้ทุกคนอ่านได้ | เห็นเฉพาะผู้ซื้อที่จองร้านนั้น (คัดลอกเข้าคำสั่งซื้อ) ร้านเห็นผู้ซื้อเป็นรหัสนิรนามเท่านั้น |
| PDPA / ข้อตกลง | ไม่มี | มีทั้งในแอปและหน้า `privacy.html`, `terms.html` (ไทย/อังกฤษ) พร้อมติ๊กยอมรับก่อนล็อกอิน บันทึกเวอร์ชันที่ยอมรับ ปุ่ม **ดาวน์โหลดข้อมูลของฉัน** และ **ลบบัญชี** |
| ภาษา | 4 ภาษา | ไทย + English เท่านั้น |
| พื้นที่เก็บข้อมูล | เก็บรูปในฐานข้อมูล | รูปอยู่ใน Storage (บีบอัดก่อนอัปโหลด) ฐานข้อมูลเก็บแต่ข้อความ + ลบออเดอร์เก่าอัตโนมัติ + ซิงก์เฉพาะส่วนที่เปลี่ยน |

## บริการที่ใช้ (ฟรี)
| ส่วน | บริการ | หมายเหตุ |
|---|---|---|
| เว็บไซต์ | GitHub Pages (repo แบบ public) | ฟรี |
| ฐานข้อมูล + ล็อกอิน + รูป | Supabase แผน Free | ดูหัวข้อ "รองรับผู้ใช้ได้เท่าไร" |
| ล็อกอิน | Google ผ่าน Supabase | ฟรี |
| กันโปรเจกต์ถูกพัก | GitHub Actions (`keepalive.yml`) | ฟรี |

## ติดตั้ง (ทำครั้งเดียว ประมาณ 30–45 นาที)

### 1) Supabase
1. สมัคร supabase.com สร้างโปรเจกต์ใหม่ (แผน Free) เลือก Region ใกล้ไทย (เช่น Singapore) **แล้วจดชื่อ Region ไว้ใส่ใน `config.js`**
2. **SQL editor** → วางทั้งไฟล์ `supabase-setup.sql` → Run (รันซ้ำได้ ไม่พัง) ไฟล์นี้สร้างตาราง กฎความปลอดภัย ฟังก์ชันที่แอปเรียก และที่เก็บรูป `menu`
3. **Authentication → Sign In / Providers**
   - เปิด **Allow anonymous sign-ins** (ให้เปิดดูร้านได้ก่อนล็อกอิน)
   - เปิด **Allow manual linking**
   - เปิด **Google** (ดูข้อ 2)
4. **Authentication → URL Configuration**: ใส่ Site URL และ Redirect URLs เป็นที่อยู่เว็บ เช่น `https://ชื่อผู้ใช้.github.io/ชื่อrepo/`
5. ปุ่ม **Connect** ด้านบน: คัดลอก **Project URL** และ **Publishable key** (ห้ามใช้ Secret / service_role)

### 2) Google (ล็อกอิน)
1. console.cloud.google.com → โปรเจกต์ใหม่ → **OAuth consent screen** (External กรอกชื่อแอป อีเมลติดต่อ ลิงก์นโยบายความเป็นส่วนตัว = `.../privacy.html` และข้อตกลง = `.../terms.html`)
2. **Credentials → OAuth client ID → Web application** ใส่ Authorized redirect URI = `https://<รหัสโปรเจกต์>.supabase.co/auth/v1/callback`
3. นำ Client ID / Secret ไปใส่ที่หน้า Google provider ใน Supabase

### 3) GitHub
1. สร้าง repository แบบ **Public** อัปโหลดไฟล์ทั้งหมดในโฟลเดอร์นี้ (รวมโฟลเดอร์ `.github`)
2. แก้ `config.js`:
   - `url` และ `key` จากข้อ 1.5
   - ส่วน `legal`: **ชื่อผู้ให้บริการ / ช่องทางติดต่อ / ที่อยู่ / Region** (ถ้าเว้นว่าง หน้านโยบายจะแสดงข้อความ "[... – set in config.js]" ห้ามเปิดสาธารณะทั้งอย่างนั้น)
3. **Settings → Pages → Source = GitHub Actions** รอแท็บ Actions ทำงานเสร็จ
4. **Settings → Secrets and variables → Actions** เพิ่ม `SUPABASE_URL` และ `SUPABASE_KEY` (publishable key) เพื่อให้ keepalive ทำงาน

### 4) ติดตั้งบนมือถือ
เปิดเว็บด้วย Chrome / Safari → เมนู → Add to Home screen

## เอกสารกฎหมาย (PDPA) – ต้องทำก่อนเปิดสาธารณะ
- ไฟล์นี้เป็น **ร่างแม่แบบ ไม่ใช่คำปรึกษากฎหมาย** ควรให้ทนายหรือที่ปรึกษา PDPA ตรวจก่อนเปิดจริง โดยเฉพาะ: ฐานทางกฎหมายแต่ละข้อ ระยะเวลาเก็บ (ออเดอร์ดิบ 30 วัน / บันทึกธุรกรรม 12 เดือน) การโอนข้อมูลไปต่างประเทศ (Supabase/Google/GitHub) อายุขั้นต่ำ 20 ปี และข้อจำกัดความรับผิด
- ถ้ากิจการเข้าข่ายต้องแต่งตั้ง DPO หรือมีบันทึกรายการประมวลผล (ROPA) ให้จัดทำเพิ่ม
- เมื่อแก้เนื้อหาสาระสำคัญ: เปลี่ยนเลขเวอร์ชันใน SQL `update cde_cfg set v='วันที่ใหม่' where k='terms_version';` และ `VERSION` ใน `legal.py`/แอป ผู้ใช้ทุกคนจะถูกขอให้ยอมรับใหม่ก่อนจอง/จัดการร้าน (เวอร์ชันปัจจุบัน 2026-10-14)
- ผู้ดูแลต้องตอบคำขอของเจ้าของข้อมูลภายใน 30 วัน และแจ้ง สคส. ภายใน 72 ชั่วโมงหากเกิดเหตุละเมิดข้อมูล

## ระบบกันโกง (บังคับที่เซิร์ฟเวอร์)
- ต้องล็อกอิน Google + ยอมรับข้อตกลง ก่อนจอง/ขาย (บัญชีไม่ระบุตัวตนทำไม่ได้)
- จองค้างได้สูงสุด 3 รายการ, จองแล้วไม่จ่ายครบ 3 ครั้งใน 24 ชม. ถูกล็อก 60 นาที, จำกัดความถี่ (เช่น 12 ออเดอร์/ชม.)
- เศษสตางค์ไม่ซ้ำต่อออเดอร์ที่เปิดอยู่ของร้านเดียวกัน (ใช้จับคู่ยอดโอน กันใช้สลิปซ้ำ)
- ผู้ซื้อที่แจ้งว่าโอนแต่ถูก 2 ร้านที่น่าเชื่อถือ (มีผู้ซื้อสำเร็จ ≥ 3 ราย) ปฏิเสธใน 30 วัน ถูกจำกัดการจอง
- ร้านใหม่ (ผู้ซื้อสำเร็จ < 3 ราย) จำกัดยอดต่อออเดอร์ 300 บาทและจำนวนออเดอร์ค้าง 5 รายการ
- ร้านที่ถูก 3 บัญชีรายงาน (ต้องเป็นออเดอร์ที่ร้านยืนยันรับเงินแล้ว) ภายใน 30 วันจะถูกซ่อนอัตโนมัติ คะแนนเฉลี่ย < 3.5 (ตั้งแต่ 5 รีวิว) ก็ซ่อนเช่นกัน
- ตรวจข้อมูลร้านที่เซิร์ฟเวอร์: ห้ามเบอร์โทร/ลิงก์/ไลน์ในชื่อ-ที่อยู่, ห้ามอวดสรรพคุณ "รักษาโรค", เครื่องสำอาง/อาหารเสริมต้องมีเลขทะเบียน, เสื้อผ้า/รองเท้าต้องมีไซซ์
- รหัสรับของสร้างโดยเซิร์ฟเวอร์ ร้านไม่เห็นรหัส ต้องสแกน/พิมพ์จากลูกค้า ใช้ซ้ำไม่ได้

### ข้อจำกัดที่ยังมี (ซื่อตรง)
- แอปไม่เชื่อมธนาคาร: ร้านเป็นคนกดยืนยันว่าได้รับเงิน ร้านทุจริต (รับเงินแล้วไม่ให้ของ) ป้องกันด้วยรายงาน/ระงับอัตโนมัติ ไม่ใช่การคุ้มครองเงิน
- ไม่มี KYC บัตรประชาชน ใช้บัญชี Google เป็นตัวยืนยัน คนทำหลายบัญชีได้ในทางทฤษฎี (ลดผลด้วยเพดานร้านใหม่/ต้องมีออเดอร์ที่ร้านยืนยัน)
- การจัดการผู้ใช้/ร้านทำผ่านหน้า Supabase Dashboard (ดูด้านล่าง) ยังไม่มีหน้าแอดมินในแอป
- ไม่มีแจ้งเตือนตอนปิดแอป (ร้านเห็นออเดอร์ใหม่เมื่อเปิดแอป/ทุก ~20 วินาทีขณะเปิดอยู่)
- แท็บ "ตู้เย็นคอนโด" ถูกซ่อนในเวอร์ชันจริง เพราะแชตยังเป็นการจำลอง
- โฆษณา AdMob ใช้ได้เฉพาะแอปที่ลงในร้านแอป เว็บไม่มีโฆษณา (รายได้มาจากผู้สนับสนุน/บริจาค หรือทำแอปมือถือทีหลัง)
- Tailwind และไลบรารี QR โหลดจาก CDN (ยังไม่ได้ฝังไฟล์) ถ้าต้องการให้เสถียรขึ้น ควร build เป็นไฟล์ของตัวเองภายหลัง

## จัดการหลังบ้าน (SQL editor / Table editor ใน Supabase)
```sql
-- ระงับ/ปลดระงับบัญชี
update profiles set banned = true where uid = 'UUID-ของผู้ใช้';
-- ซ่อนร้าน / ยกเว้นการระงับอัตโนมัติ (หลังตรวจแล้วว่าไม่ผิด)
update shops set paused = true where id = 123;
update shops set cleared = true where id = 123;
-- ดูรายงานที่เข้ามา
select o.id, o.shop_id, o.report, o.created_at from orders o where report is not null order by id desc;
-- ล้างข้อมูลเก่า/ลบสินค้าหมดอายุ/คิวลบรูปด้วยมือ (ปกติ pg_cron รันให้ทุกเที่ยงคืนไทย)
select cde_nightly();
-- ดูขนาดฐานข้อมูล/รูป/คิว
select cde_usage();
```
ถ้าไม่ได้เปิด extension `pg_cron` (Database → Extensions) ให้รัน `select cde_nightly();` ทุกวัน (หรืออย่างน้อยสัปดาห์ละครั้ง

## ตั้งค่าระบบลบอัตโนมัติ + ลบรูป (ทำครั้งเดียวหลังรัน SQL)
ระบบทำงานอัตโนมัติ **ทุกเที่ยงคืนเวลาไทย** (17:00 UTC) ลบสินค้าหมดอายุ แล้วลบรูปใน Storage ให้ด้วย ต้องเปิดส่วนเสริมของ Supabase 2 ตัว:
1. **Database → Extensions** เปิด `pg_cron` และ `pg_net` (ถ้าไฟล์ SQL รันแล้วยังไม่เห็นงานตั้งเวลา ให้เปิดสองตัวนี้แล้วรันไฟล์ SQL ซ้ำอีกครั้ง)
2. บอกฐานข้อมูลว่าโปรเจกต์ชื่ออะไร และเก็บกุญแจลบไฟล์ไว้ใน Vault (อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น **ห้ามใส่ในแอปหรือ config.js**) — SQL editor:
```sql
update cde_cfg set v = 'https://รหัสโปรเจกต์.supabase.co' where k = 'project_url';
select vault.create_secret('วาง Secret key (หรือ service_role key) ที่นี่', 'cde_service_key');
```
3. ลองรันมือ: `select cde_nightly();` แล้ว `select cde_usage();` ดูขนาดฐานข้อมูล/รูป (ตรวจว่า `images.configured` เป็น `true`)

**ทำงานอย่างไร**
| อะไร | เมื่อไหร่ | ผล |
|---|---|---|
| ลบสินค้าที่ **หมดอายุ** และ **อาหารของวันก่อน** (ยกเว้นรายการ "เมนูประจำ" ที่ร้านตั้งไว้) พร้อมเซ็ต/กล่องที่เกี่ยวข้อง | ทุกเที่ยงคืนไทย | รายการหายจากระบบ ร้านต้องกดเปิดขายใหม่ตอนเช้า (เมนูประจำช่วยให้ทำเร็ว) |
| **trigger ลบรูป**: ทุกครั้งที่สินค้า/ร้าน/บัญชีถูกลบ หรือเปลี่ยนรูป ชื่อไฟล์เก่าจะเข้าคิวลบ | ทันทีที่ข้อมูลเปลี่ยน | ไฟล์รูปไม่ค้างใน Storage |
| ส่งคำสั่งลบไฟล์ไปที่ Storage API (retry สูงสุด 5 ครั้ง) | ทุก 15 นาที และหลังงานเที่ยงคืน | คืนพื้นที่รูป |
| กวาดรูปกำพร้า (อัปโหลดแล้วไม่ได้ใช้ เกิน 1 วัน) | ทุกเที่ยงคืน | กันพื้นที่รั่ว |
| ลบรายละเอียดออเดอร์ดิบ (รหัสรับของ ข้อมูลบัญชีที่คัดลอก) | 30 วันหลังจบ | ลดขนาด |

> หมายเหตุสำคัญ: การลบไฟล์ใน Storage ต้องเรียกผ่าน Storage API (การลบแถวใน SQL ไม่คืนพื้นที่จริง) จึงใช้ `pg_net` + Vault ถ้า `pg_net`/Vault ไม่พร้อม คิวจะค้างและไม่ลบไฟล์ (ตรวจด้วย `cde_usage()` ที่ช่อง `image_queue`) — **ส่วนนี้ผมทดสอบกับ Postgres จำลองเท่านั้น ยังไม่ได้ทดสอบกับ Supabase จริง ให้ทดลอง: อัปโหลดรูป → ลบสินค้า → รัน `select cde_flush_images();` → ดูว่าไฟล์หายใน Storage**

## ประวัติการซื้อขาย (หลักฐานเมื่อลูกค้าโวย)
- ทุกออเดอร์มี **เลขที่ออเดอร์** (เช่น `CD00000123`; ไม่ใช่รหัสรับของ ซึ่งเป็นความลับ) ระบบเขียน "สมุดบัญชีธุรกรรม" (`order_ledger`) อัตโนมัติด้วย trigger แถวละ ~250 ไบต์ เก็บ: เลขออเดอร์ ร้าน สินค้า จำนวน ยอดเงิน (รวมเศษสตางค์) เวลาที่จอง/แจ้งโอน/ร้านยืนยัน/รับของ ผู้ยกเลิก การรายงาน ชื่อผู้รับเงิน + เลขท้าย 4 หลักของบัญชี
- **เก็บ 12 เดือน** (ปรับได้: `update cde_cfg set v='6' where k='ledger_months';`) แม้สินค้า ร้าน หรือออเดอร์ดิบถูกลบไปแล้ว ผู้ซื้อเปิดดูได้ที่แท็บคำสั่งซื้อ → "ประวัติธุรกรรม" ร้านดูได้ที่หน้าจัดการออเดอร์ (เห็นผู้ซื้อเป็นรหัสนิรนาม)
- ข้อพิพาท: ขอเลขออเดอร์จากลูกค้า แล้วค้นใน SQL editor: `select * from order_ledger where order_id = 123;` (ตัวเลขท้ายเลขออเดอร์ตัด 0 นำหน้า)
- ข้อจำกัดตรง ๆ: แอปไม่เห็นเงินในธนาคาร จึงเป็นหลักฐานว่า "ใครกดอะไรเมื่อไหร่ ยอดเท่าไหร่ ให้ใครโอน" ไม่ใช่หลักฐานว่าเงินเข้าจริง สลิปธนาคารของลูกค้ายังต้องใช้ประกอบ
- เมื่อผู้ใช้ลบบัญชี แถวธุรกรรมยังอยู่ตามระยะเวลาข้างต้นแต่ตัดการเชื่อมกับตัวบุคคล (ระบุไว้ในนโยบายความเป็นส่วนตัวแล้ว)
- **ไม่เก็บประวัติแชต**: แชตตู้เย็นคอนโดถูกซ่อนในเวอร์ชันจริง และไม่มีตารางเก็บแชตในฐานข้อมูลเลย ถ้าเปิดฟีเจอร์แชตจริงในอนาคต ต้องออกแบบให้ลบอัตโนมัติ (เช่น 24–72 ชม.) ก่อน

## รองรับผู้ใช้ได้เท่าไร และโตแล้วทำอย่างไร
ออกแบบให้ "ข้อมูลหมุนเวียน ไม่สะสม":
- **รูปไม่อยู่ในฐานข้อมูลหลัก** อยู่ใน Storage (ไฟล์ละ ≤ 200 KB) และถูกลบพร้อมสินค้า
- **สินค้าลบรายวัน** ตารางสินค้า/สต็อกจึงเล็กและไม่โตตามเวลา
- **ออเดอร์ดิบ 30 วัน + สมุดบัญชีแบบย่อ 12 เดือน** เป็นก้อนเดียวที่โตตามจำนวนธุรกรรม
- ซิงก์เฉพาะส่วนที่เปลี่ยน ไม่ใช้ realtime (เพดานเชื่อมต่อพร้อมกันของแผนฟรีต่ำ)
- **ประมาณการหยาบ (ยังไม่ได้ทดสอบโหลดจริง):** สมุดบัญชี ~250–350 ไบต์/ออเดอร์รวมดัชนี, ออเดอร์ดิบ ~1 KB/ออเดอร์ (เก็บ 30 วัน)
  | สมมติ | ออเดอร์/เดือน | ฐานข้อมูลโดยประมาณ (เก็บ 12 เดือน) |
  |---|---|---|
  | 10,000 คน × 5 ออเดอร์/เดือน | 50,000 | ~200–250 MB ✔ อยู่ในแผนฟรี |
  | 20,000 คน × 5 ออเดอร์/เดือน | 100,000 | ~450–550 MB ⚠ ชนเพดาน → ตั้ง `ledger_months` เป็น 6 (~250–300 MB) หรืออัปเกรด |
  ยังไม่รวมข้อมูลระบบของ Supabase เอง (หลักสิบ MB) ผู้ใช้ที่ "ออเดอร์น้อยกว่านี้" รองรับได้มากกว่า ตัวเลขจริงดูจาก `select cde_usage();`
- รูป: เมื่อสินค้าถูกลบรายวัน พื้นที่ Storage 1 GB หมุนเวียนได้ (รูปเฉลี่ย ~50–110 KB ≈ หมื่นรูปพร้อมกัน)
- ตัวเลขเพดานแผนฟรี (ฐานข้อมูล 500 MB / รูป 1 GB / ทราฟฟิกออก 5 GB ต่อเดือน / ผู้ใช้ 50,000 MAU / พักโปรเจกต์ถ้าเงียบ 1 สัปดาห์) มาจากข้อมูลสาธารณะที่ค้นได้ **ตรวจที่ supabase.com/pricing ก่อนเปิดจริง**
- **เมื่อใช้ถึง ~70%** (ดู `cde_usage()` หรือ Supabase → Reports) อัปเกรดแผน Pro (ราว 25 ดอลลาร์/เดือน ≈ 900 บาท ตรวจราคาล่าสุดที่หน้า pricing) **ไม่ต้องแก้โค้ด** จ่ายจากรายได้ผู้สนับสนุน/บริจาค; ค่าใช้จ่ายส่วนเกินแบบจ่ายตามใช้ขึ้นกับตัวเลขที่ Supabase กำหนด
- **อยากย้าย:** ตารางและฟังก์ชันเป็น Postgres มาตรฐาน `pg_dump` ย้ายได้ ส่วนที่ผูกกับ Supabase คือระบบล็อกอิน (`auth.uid()`/`auth.jwt()`) Storage และ pg_cron/pg_net/Vault ต้องหาของทดแทนเมื่อย้าย
- **ทำไมไม่ใช้ Cloudflare D1 ฟรี:** ตั้งแต่ 1 ก.ย. 2026 D1 แผนฟรีตัดการทำงานเมื่อเกินโควตาอ่าน/เขียนรายวัน
- ไม่มีบริการฐานข้อมูลฟรีที่ "รับผู้ใช้ไม่จำกัด" ทางที่ปลอดภัยคือ: เริ่มฟรี → ดูตัวเลขจริง → อัปเกรดก่อนชนเพดาน

## เช็กลิสต์ก่อนเปิดสาธารณะ
1. ให้ทนาย/ที่ปรึกษา PDPA ตรวจ `privacy.html` / `terms.html` และกรอกข้อมูลใน `config.js` ให้ครบ
2. ทดสอบเต็มรอบด้วยบัญชี Google 3 บัญชี (ร้าน / ผู้ซื้อ / คนที่ 3) บนมือถือจริง: สมัครร้าน → จอง → โอน → ร้านยืนยัน → สแกนรับของ → รายงาน → ลบบัญชี
3. ตรวจใน Supabase ว่า Table editor แสดงว่าตารางทั้งหมด **RLS enabled** และไม่มี policy (ถูกต้อง: เข้าถึงผ่านฟังก์ชันเท่านั้น)
4. ตั้งการแจ้งเตือนอีเมลของ Supabase เมื่อใช้โควตาใกล้เต็ม
5. เตรียมช่องทางรับเรื่องร้องเรียน/คำขอตามสิทธิ์ PDPA และคนที่ตอบภายใน 30 วัน
